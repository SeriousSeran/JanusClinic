01 · Learn the vocabulary

The pieces, in ordinary language.

A website is a collection of parts. Understanding their jobs prevents you from buying or building things you do not yet need.

TermWhat it means for Janus
FrontendThe pages patients see: text, photos, menus, treatment lists, and buttons.
Source codeThe editable instructions used to build those pages. Shared source makes one change apply consistently across many pages.
ComponentA reusable building block, such as the same header, product card, or booking button on every relevant page.
Content modelA consistent set of fields. A product might have a name, photo, price, description, and order link.
Backend / databaseServer services that store or process information. A brochure site does not automatically need either.
GitHubA versioned home for code. It helps you see changes and return to earlier versions; code backup does not back up a separate database.
Hosting / deploymentA service that runs the site online, and the act of putting an approved version there.
Domain / DNSThe clinic’s address and the settings that point that address to its hosting service.
HTTPSEncryption between a visitor and the site. It is essential, but does not by itself make forms, accounts, or stored data safe.
Preview / productionA place to review work versus the version real patients use. Treat a public preview as public information.
Useful mental model: Lovable can help build and host. GitHub stores code history. Your domain is the public address. The clinic still owns content accuracy, account access, and decisions about patient information.

02 · Understand what you have

A strong visual reference.
The editable foundation comes next.

Already prepared

  • 43 public pages and 63 captured assets, with original clean routes.
  • A local Node.js server and checks for file integrity, links, and representative browser behavior.
  • A design portfolio at /portfolio, exact design guidance in docs/design-identity.md, and instructions for agents in AGENTS.md.
  • Reference covers of all 43 original pages and six representative mobile screens.

What the capture is

It contains rendered HTML, CSS, images, fonts, and compiled browser code. It preserves what visitors can see. It is not the original editable React/Next.js project, clinic database, booking system, or administrative dashboard.

A large change to visible HTML can conflict with embedded browser data. That is why “the page looks right” and “the site is easy to maintain” are different milestones.

What has and has not been proved

The public pages, local navigation, images, and representative interactions have been checked. Contact success was tested with a simulated provider response. Real enquiry delivery, a live Lovable deployment, and a production security review have not been verified.

Your next useful milestone: make one representative group of pages from editable components and content, then demonstrate that changing a shared header or treatment updates every intended place.

Keep the captured version as a reference while rebuilding. Do not overwrite the only working copy to experiment.

04 · Think like a designer

Preserve identity through rules.

A designer would record the repeated decisions, not simply collect attractive screenshots.

PaletteIvory #FAF7F4; stone #F0EBE3; deeper stone #E8E0D5; charcoal #1A1A1A; muted gray #6B6560; gold #C9A97A.

A useful editing exercise

  1. Pick one treatment page and compare desktop and mobile references.
  2. Change only its confirmed description in the editable version.
  3. Verify that the heading, spacing, image crop, and consultation action still match the template.
  4. Ask another person to check readability and whether the treatment is understandable.
Avoid drift: do not let an agent replace the font pairing, invent a logo, add unrelated gradients, or turn every control into a large rounded pill. If you want a redesign, decide that explicitly.

Read the full identity guide before styling changes. Use the portfolio as a reference, not as a patient-facing sales page.

05 · Think like a security reviewer

Start with the information flow.

For a first public version, patients should be able to read services, find the clinic, and request an appointment. They do not need a patient account or a medical-record database just to do that.

Draw this simple map

Patient browser → page or form → receiving service → clinic staff → retention or deletion.

For every arrow, ask what information is sent, whether it is needed, who can see it, and what happens if the service fails.

  • Minimize collection: basic appointment details first. Do not invite medical reports, identity documents, or detailed health histories into an unreviewed contact form.
  • Verify forms: check required fields in both browser and receiving service, abuse/spam controls, error states, and that the correct clinic account receives the enquiry.
  • Protect secrets: private API keys belong in the platform’s secure configuration, not page code, GitHub, PDFs, or prompts.
  • Protect accounts: use clinic-owned accounts, multi-factor authentication, individual staff access, and a backup owner.
  • Review external services: document form, messaging, analytics, map, and hosting providers. Decide what data each may receive and update the privacy notice.
  • Check the deployment: HTTPS, dependency findings, appropriate security headers, safe error messages, and no private data in logs or public pages.

Have the clinic confirm applicable Sri Lankan privacy and health-data obligations and the suitability of third-party storage before collecting sensitive information.

A future patient portal needs its own plan: authentication, server-enforced access, data isolation, audit history, retention, recovery, and specialist review. Do not assume a public website builder supplies those decisions automatically.

06 · Evaluate Lovable

A reasonable tool.
A deliberate migration.

Recommendation: use Lovable for an editable public information and booking-request website, with a small pilot before migrating everything.

What the current documentation says

  • Website import: paste a public URL. Lovable rebuilds visible pages as editable project code. It does not recover the original server or form-delivery behavior.
  • Adding pages: up to 10 pages per request; the documented limit is 30 page reads per hour, including comparison reads. Import and comparison consume credits.
  • Rollout: website and ZIP project import may not yet appear in every account.
  • Code import: Upload code accepts a ZIP and rebuilds it as a Lovable project. The docs currently describe TanStack Start as the rebuild stack. Our capture is reference material, not original application source.
  • GitHub sync: connecting a project creates a new repository. It does not simply attach Git sync to this existing JanusClinic repository. Keep the original as a baseline.

The maintainability trap

Website import adds separate copies of headers, footers, and navigation to pages. Products and journal posts arrive as fixed pages rather than manageable records. Ask for shared components and a content model, otherwise editing remains repetitive.

If import is unavailable: start a Lovable project with the identity guide, original assets, representative screenshots, and a precise page brief. Build a small pilot. Another option is a developer-led rebuild with GitHub and a different host; that offers more control but requires more technical ownership.

Product features and limits can change. Official links and the verification date are on the final page.

07 · Your first Lovable session

Build a pilot you can judge.

  1. Use a clinic-owned account. Check who owns the workspace, billing, domain, and backups.
  2. Keep the original site online. Do not change DNS or replace the existing hosting yet.
  3. If available, import the homepage. Dashboard → + → Import project to Lovable → Website. Use the full public URL and confirm ownership or permission when Lovable asks.
  4. Provide the identity guidance. Share the design guide and selected reference screenshots. The local portfolio URL is not accessible to Lovable; supply files or public source URLs.
  5. Add representative templates. Start with a service listing, one treatment, a product page, an article, and Contact. Work in small batches.
  6. Ask for shared source. Consolidate Header, Footer, Layout, Button, Card, FormField, and typography tokens. Put repeated content in consistent editable structures.
  7. Demonstrate an edit. Change one confirmed treatment description and one shared navigation label. Verify the intended pages update without visual drift.

A starter prompt

Build an editable pilot of Janus Estheti Clinique.
Preserve the supplied identity guide, original logo, local fonts,
photography, clean routes, and desktop/mobile layouts.
Use shared components and structured content, not separate copies
of every header and footer. Do not invent clinical claims or prices.
Keep booking as an appointment request, not a confirmed slot.
List what works, what is simulated, and what still needs setup.

Do not assume import success means the clinic can receive messages. Verify the chosen booking/contact workflow separately.

08 · Make content easy to change

One change, one known place.

The aim is to edit a treatment or product without manually repairing the same information across multiple pages.

Content typeExample fieldsWho approves it
TreatmentSlug, title, category, description, image, suitability, process, FAQs, booking text.Clinical lead
ProductSlug, name, category, image, price in LKR, usage, availability and order link.Clinic/product owner
ArticleSlug, title, summary, author, publication/review dates, cover, article body and metadata.Clinical/editorial reviewer
Clinic settingsPhone, email, address, hours, map, logo, social destinations.Clinic manager

Start with the simplest adequate editor

Structured files are often enough when one person and an agent make occasional changes. If several nontechnical staff need frequent editing, evaluate a CMS later. A CMS is an editing tool; it is not automatically a patient-record system.

Migrate the remaining pages

  1. Use the 43-page inventory to track each route and template.
  2. Add pages in manageable batches; review imported duplicates and keep shared components shared.
  3. Check all treatment, product, article, legal, and contact routes—not just the homepage.
  4. Keep existing URLs where practical. Define redirects for intentional changes.
  5. Restore descriptions, canonical URLs, and structured metadata deliberately; website import does not copy every SEO field.
First-version scope: public information, useful product details, articles, clinic contact, and appointment requests. Add accounts, payments, or clinical records only when there is a clear need and a separate design.

09 · Check quality like an engineer

Ask for evidence, not “done.”

CheckWhat you should see
Content and routesEvery intended page exists; links work; unknown addresses show a useful 404; prices, hours and credentials are approved.
Desktop and mobileReadable headings, sensible image crops, usable menus, no horizontal overflow, and consistent spacing.
AccessibilityKeyboard navigation, visible focus, meaningful labels and alt text, readable contrast, and a sensible heading order.
Form behaviorRequired/invalid fields, success and failure states, spam handling, and confirmed clinic delivery using an approved test enquiry.
PerformanceReasonable image sizes, lazy loading where appropriate, local/reliable fonts, and acceptable behavior on a real phone and slower connection.
Search and sharingCorrect titles, descriptions, canonical URLs, sitemap, indexability, social previews, and accurate clinic structured data.
Security and privacyNo exposed private keys; reviewed providers and personal-data flow; access rules tested for any restricted feature.

In this repository

npm run check          # original capture and local references
npm test               # local HTTP server behavior
npm run test:browser   # browser routes and interactions

These commands validate this repository. A new Lovable project needs equivalent checks for its actual generated source and hosting. Passing the old capture’s checks does not validate a new deployment.

During development, simulate external form responses. Before launch, arrange a controlled live test with clinic staff, using test details rather than real patient information.

10 · Launch with a concrete plan

Make the public version deliberate.

  1. Approve the scope and content. The clinic reviews treatment statements, contact details, prices, imagery, privacy information, and the booking process.
  2. Resolve critical findings. Run the platform’s security checks and review relevant findings. A clean scanner is useful evidence, not a complete security assessment.
  3. Publish a review version. Lovable’s Publish flow lets you choose the audience. A patient website needs Public access when it is ready. Keep sensitive content out of public previews.
  4. Verify the actual published URL. Open it signed out on a real phone. Test deep links, images, menus, sharing metadata, and the approved enquiry journey.
  5. Connect the clinic domain. Follow the current Custom domains instructions. Copy the exact records Lovable provides and confirm HTTPS works.
  6. Preserve email settings. Review the existing DNS records before changing anything. Do not delete MX/TXT or other records used by clinic email or services.
  7. Check search setup. Use the final domain in canonical URLs and sitemap. Remove staging-only noindex from patient pages when appropriate; keep internal reference material separate.
  8. Monitor the switch. Ask clinic staff to verify enquiries and important pages. Keep the previous hosting and a documented rollback path until the new version is stable.
Rollback means a plan, not a button: record the previous deployment or DNS target and who can restore it. DNS changes are not instant; caches and record TTLs affect how quickly visitors move.

Updating code in an editor does not automatically update the published site. Lovable’s current documentation says to use Publish changes for later releases.

11 · Keep it healthy after launch

Give the website an owner.

WhenSimple routine
Every content changeConfirm the information, review the affected template on phone and desktop, test the relevant journey, and record the version.
WeeklyCheck contact delivery, phone/WhatsApp destinations, hours, promotions, and obvious broken links. Review reports of problems.
MonthlyReview dependency/security findings, access permissions, provider bills, and site performance. Update what is relevant and retest.
Quarterly or after major changesReview clinical and privacy content, ownership, recovery access, and the rollback instructions. Revisit whether the current editing workflow still fits.

Keep a small handoff pack

  • Page inventory and content ownership.
  • Identity guide and component reference.
  • How to edit, test, publish, and restore a previous version.
  • Which providers receive enquiries and how long information is kept.
  • Account owners and recovery procedures; store passwords and recovery codes securely, not in the repository.

Understand what a backup covers

GitHub records code versions. Separately managed content, databases, uploaded files, and provider settings need their own recovery plan if you introduce them. Practice restoring a test copy before depending on a backup.

A website without accounts or a database can be simpler to operate. Add complexity when it serves a real clinic workflow, not because a builder makes it easy to generate.

13 · Your next steps and sources

A small plan you can finish.

  1. Review the identity portfolio. Confirm that it describes the Janus look you want to keep.
  2. Create a Lovable pilot. Import or rebuild representative pages; check whether your account has the import feature.
  3. Prove editing works. Shared components, structured content, and one demonstrated update before scaling to all pages.
  4. Choose the enquiry workflow. Confirm the clinic recipient and data policy.
  5. Complete the quality checklist. Then review a published preview before moving the domain.

Ready for patients?

  • Clinic-approved content and ownership
  • All intended pages and mobile navigation checked
  • Booking/enquiry delivery confirmed in a controlled live test
  • Privacy, data handling, and relevant security findings reviewed
  • Public access, domain, HTTPS, metadata, and email DNS checked
  • Named maintainer, recovery access, and rollback instructions
